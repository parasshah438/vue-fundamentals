Nuxt.js Complete Guide for Real Projects

This guide explains what Nuxt.js is, where to use it, why teams choose it, how to set up a new project, and how to move an existing Vue or frontend codebase into Nuxt. It covers routing, SSR, SSG, Nitro APIs, middleware, modules, SEO, deployment, testing, and production patterns with short examples and clear commands.

A practical map of Nuxt from first install to production deployment.

  • Set up both new Nuxt apps and migration paths for existing projects.

  • Use short examples, common commands, and interview-ready answers.

What is Nuxt.js?

Nuxt.js is the application framework built on top of Vue 3. It adds file-based routing, server rendering, static generation, server API handlers, metadata management, layout conventions, auto imports, and deployment-friendly tooling so you can build SEO-aware and production-ready apps faster than wiring everything manually with plain Vue.

Vue first

You still write Vue components with script setup, props, slots, and composables.

Framework layer

Nuxt adds conventions for pages, layouts, middleware, and server code.

SEO friendly

SSR, SSG, and head management make content visible to crawlers and social previews.

Full stack ready

Nitro server routes, runtime config, and deployment adapters are built in.

Where We Use Nuxt.js

Nuxt is strongest when the application needs more than a browser-only SPA. It fits content-heavy websites, marketing pages, product catalogs, SaaS dashboards with public pages, and apps that want frontend and lightweight backend logic in one repo.

Project typeWhy Nuxt fitsShort example
Marketing or company websiteSSR + SEO + metadata + static generationAgency site, service pages, blogs
Content platformDynamic routes, cached data, clean URLs, image optimizationDocumentation portal, CMS frontend
Ecommerce storefrontServer rendering, product SEO, hybrid rendering, server API proxyCatalog, PDP pages, checkout frontend
SaaS app with public and private pagesPublic SEO routes plus authenticated dashboard routes in one appLanding pages + user workspace
Frontend for existing backendRuntime config, composables, middleware, server routes for BFF patternsLaravel API + Nuxt frontend

Why Use Nuxt.js?

Short answer: Nuxt removes a large amount of manual setup around Vue applications and gives you routing, rendering strategy, SEO, data conventions, and server capabilities in one coherent framework.

1
Faster setup

You avoid hand-wiring router, SSR infrastructure, head management, and deployment adapters from scratch.

2
Better SEO and first load

SSR, prerendering, and hybrid rendering improve discoverability and perceived speed.

3
Strong conventions

Pages, layouts, composables, plugins, and server routes live in predictable places.

4
One repo, full stack options

Nitro lets you add backend handlers, proxy logic, and scheduled tasks without a separate Express layer.

How Nuxt.js Works

Nuxt sits between your Vue components, the server runtime, and the browser. It decides how routes are generated, how data is fetched, and whether a page is rendered on the server, generated ahead of time, or hydrated in the browser.

Vue code

Pages, components, and composables are authored with Vue 3.

Nuxt conventions

Nuxt turns files into routes, layouts, plugins, middleware, and server handlers.

Nitro server

Nitro executes SSR, APIs, caching, and deployment adapters.

Browser

The browser receives HTML, CSS, JS, and hydrated Vue interactivity.

Typical Request Pipeline
Request Route match Middleware Fetch data SSR / SSG Hydration

How to Move an Existing Project Into Nuxt

There is no single migration path because existing projects differ. The safest pattern is to create a fresh Nuxt shell, then move views, components, routes, state, and API calls incrementally.

Existing Vue SPA

Move route views into app/pages/, shared UI into app/components/, and router logic into file-based routes.

Existing static frontend

Use Nuxt for structured routes, SEO, forms, and deployment without a separate SPA router.

Existing backend API

Keep the backend and let Nuxt consume it via runtime config, composables, and server proxies.

1Migration checklist
  1. List current routes, layouts, environment variables, and third-party integrations.
  2. Create a clean Nuxt app and commit it before moving business logic.
  3. Move top-level screens into app/pages/ and shared wrappers into app/layouts/default.vue.
  4. Move app-side shared logic into app/composables/ and server logic into root-level server/api/ when it truly belongs in the frontend repo.
  5. Replace manual router config with folder names and dynamic segments.
  6. Convert global state into Pinia or Nuxt useState() where appropriate.

Nuxt 4 default: new starters use an app/ source directory by default. Existing projects can still keep the older root-level structure because Nuxt auto-detects it, but new work should generally follow the newer layout.

2Existing Vue + Vite to Nuxt flow

Laravel API and Nuxt.js Project Setup Flow

A very common real-world stack is Laravel as the backend API and Nuxt as the frontend application. Laravel handles database, authentication, validation, queues, mail, and business logic. Nuxt handles pages, UI, SSR, SEO, routing, and the browser experience.

Laravel backend

Owns models, migrations, controllers, policies, jobs, mail, and API endpoints.

Nuxt frontend

Owns SEO pages, dashboard UI, layouts, route rendering, and user-facing interactions.

Auth flow

Laravel Sanctum or token auth protects APIs while Nuxt uses middleware and server-aware fetches.

Deployment split

You can deploy Laravel and Nuxt separately, or place them behind the same domain for easier cookie auth.

1Recommended project structure
workspace/
  laravel-api/
  nuxt-frontend/

Browser  ->  Nuxt pages / SSR  ->  Laravel API  ->  MySQL

Recommended responsibility split: keep business rules, payments, admin logic, and protected data in Laravel. Use Nuxt for public pages, SEO, product UI, dashboards, and rendering strategy.

6Laravel + Nuxt working flow
1. Build the backend first

Create Laravel models, migrations, controllers, and API routes before wiring the frontend screens.

2. Point Nuxt to the API

Store the backend URL in runtimeConfig.public.apiBase so local, staging, and production environments stay flexible.

3. Render SEO pages with Nuxt

Marketing pages, blogs, docs, and public product routes should live in Nuxt for SSR, prerendering, and head management.

4. Protect private routes carefully

Use Nuxt middleware for redirects, but keep the real permission checks in Laravel for protected API access.

Nuxt 4 What Changed

Nuxt 4 is a developer-experience-focused major release. The biggest visible changes are the new app/ project structure, smarter data fetching behavior, improved TypeScript separation, and faster CLI and development performance.

New app/ structure

Fresh projects now place most Vue app code inside app/, while server/, public/, and shared/ stay at the root.

Smarter data layer

useAsyncData and useFetch now share keyed state better, clean up unmounted data, and support reactive keys more consistently.

Better TypeScript

Nuxt now generates separate TS contexts for app, server, shared, and node/build code for cleaner IntelliSense and safer type checks.

Faster dev tooling

Cold starts, file watching, and CLI communication are faster, especially on Windows and Linux.

Nuxt 4 changeWhat it means in practiceWhat you should do
app/ default source directoryPages, layouts, plugins, components, and composables now default under app/.Use the new layout for fresh projects; keep old structure only when maintaining existing apps.
Shared data-fetching behaviorSame-key fetches share refs and fetch options matter more.Keep keys stable and avoid conflicting options for the same explicit key.
Shallow data defaultsFetched data is optimized for performance and should usually be treated as immutable.Use deep: true only when you truly need deep reactivity.
TS project splittingApp, server, shared, and builder code are typed in more accurate contexts.Run typecheck after upgrade and move shared types into shared/ when needed.

Routing in Nuxt.js

Nuxt uses file-based routing. In current Nuxt 4 starters, you create route files inside app/pages/, and Nuxt maps them to URLs automatically.

    app/pages/blog/index.vue         -> /blog
    app/pages/blog/[slug].vue        -> /blog/my-post
    app/pages/users/[id]/edit.vue    -> /users/42/edit

Composables and State

Composables are shared logic functions. Nuxt also provides useState() for SSR-safe shared state across requests and hydration.

// app/composables/useCart.ts
export const useCart = () => {
  const items = useState<{ id: number; name: string; qty: number }[]>('cart', () => []);

  const addItem = (item: { id: number; name: string; qty: number }) => {
    items.value.push(item);
  };

  const totalQty = computed(() => items.value.reduce((sum, item) => sum + item.qty, 0));

  return { items, addItem, totalQty };
};
Use useState()

For lightweight shared state that should work across SSR and client hydration.

Use Pinia

For larger apps needing structured stores, actions, modules, and devtools inspection.

Data Fetching in Nuxt

Nuxt gives you several data utilities. The most common are useFetch(), useAsyncData(), and $fetch(). Choose the right one based on whether you want SSR integration, caching, or manual control.

UtilityBest useExample
useFetch()Simple SSR-aware API fetchingPage data, public lists, detail pages
useAsyncData()Custom async logic with keysCombined queries, custom transform logic
$fetch()Direct request without composable state wrapperButton click, form submit, plugin helper

Nitro Server API

Nuxt uses Nitro for server routes. Files inside server/api become backend endpoints, and they can run on Node, serverless, or edge-compatible targets depending on deployment.

// server/api/posts.get.ts
export default defineEventHandler(async () => {
  return [
    { id: 1, title: 'Nuxt Basics', summary: 'Routing and layouts' },
    { id: 2, title: 'Nuxt Server API', summary: 'Nitro handlers' },
  ];
});
// server/api/contact.post.ts
export default defineEventHandler(async (event) => {
  const body = await readBody(event);

  if (!body.email) {
    throw createError({ statusCode: 422, statusMessage: 'Email is required' });
  }

  return { ok: true, message: 'Form received', data: body };
});

Rule of thumb: put simple frontend-adjacent backend tasks in Nitro, but keep heavy domain systems in a dedicated backend if they already exist and are owned independently.

Middleware

Route middleware runs before entering a page. Use it for authentication checks, redirects, locale selection, or guarding dashboard areas.

// app/middleware/auth.ts
export default defineNuxtRouteMiddleware((to) => {
  const token = useCookie('auth_token');

  if (!token.value && to.path.startsWith('/dashboard')) {
    return navigateTo('/login');
  }
});

Modules and Plugins

Modules extend Nuxt at the framework level. Plugins register app-wide behavior or third-party libraries during startup.

Popular modules

@pinia/nuxt, @nuxt/image, @nuxtjs/tailwindcss, @nuxtjs/sitemap, @nuxt/content.

Plugin use case

Inject an Axios instance, analytics client, date formatter, or auth helper into the app context.

// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['@pinia/nuxt', '@nuxt/image'],
});
// app/plugins/api.ts
export default defineNuxtPlugin(() => {
  const config = useRuntimeConfig();

  const api = $fetch.create({
    baseURL: config.public.apiBase,
  });

  return {
    provide: {
      api,
    },
  };
});

Nuxt supports multiple rendering strategies. Pick the one that matches freshness, SEO, and hosting needs.

ModeMeaningBest for

SSG / prerenderGenerate ahead of timeLanding pages, docs, blogs, static content

    '/products/**': { swr: 300 },
    '/api/**': { cors: true },
  },
});

Authentication and Security

Nuxt does not force one auth library, which is usually a strength. The common pattern is cookie-based auth via your backend or a module such as sidebase auth, combined with route middleware and server checks.

Frontend guard

Use route middleware to block pages and redirect guests.

Backend verification

Always validate tokens or sessions in server routes too, not only on the client.

// server/api/me.get.ts
export default defineEventHandler(async (event) => {
  const token = getCookie(event, 'auth_token');

  if (!token) {
    throw createError({ statusCode: 401, statusMessage: 'Unauthenticated' });
  }

  return { id: 1, name: 'Paras', role: 'admin' };
});

Security basics: validate input, keep secrets in runtime config, sanitize uploaded content, protect server handlers, and do not trust client route guards alone.

Runtime Config and Environment Variables

Nuxt uses runtime config to separate private server-only values from public client-exposed values.

    public: {

  },
});

Nuxt Interview Q and A

This section is designed for interview revision from beginner to advanced level. The answers are intentionally short, direct, and easy to speak in an interview, but still technically correct.

Basic

Core Nuxt purpose, folders, rendering, and routing questions.

Intermediate

Data fetching, state, middleware, modules, plugins, and runtime config.

Advanced

Hydration, route rules, caching, deployment, performance, and Nuxt 4 changes.

Scenario

Real-world architecture answers for SEO, auth, APIs, and hybrid rendering.

1Basic Nuxt Interview Questions
QuestionShort answer
What is Nuxt?Nuxt is a framework built on top of Vue that gives you file-based routing, rendering modes, server features, SEO helpers, and app structure out of the box.
What is the difference between Vue and Nuxt?Vue is the core UI library, while Nuxt is the application framework around Vue for building full apps faster.
When should you choose Nuxt over Vue + Vite?Use Nuxt when you need SSR, SSG, SEO, predictable routing, or backend-style server handlers in the same project.
What is file-based routing?Nuxt creates routes from files inside app/pages/, so you do not write a large manual router config for common page routes.
What is Nitro in Nuxt?Nitro is Nuxt's server engine for SSR, server routes, caching, adapters, and deployment targets.
What is inside the app/ directory in Nuxt 4?It usually contains app-side Vue code such as pages, layouts, components, composables, plugins, and app.vue.
What is the purpose of app.vue?It is the root app shell and often wraps the whole app with common layout-level structure.
What does useHead() do?It lets you define title, meta tags, canonical tags, and other head elements in a reactive Nuxt-friendly way.
2Intermediate Nuxt Interview Questions
QuestionShort answer
What is useFetch()?It is a Nuxt composable for SSR-aware fetching that returns reactive values like data, pending, status, and error.
What is the difference between useFetch() and $fetch?useFetch() integrates with SSR and reactive state, while $fetch is a lower-level fetch utility for imperative requests.
What is the difference between useFetch() and useAsyncData()?useFetch() is focused on HTTP requests, while useAsyncData() is more general and can wrap any async function.
How do you protect a route in Nuxt?Use route middleware for navigation checks and always re-check auth or permissions on the server or backend side too.
What is route middleware?It is logic that runs before navigation and is commonly used for auth checks, redirects, or route conditions.
What is the difference between a Nuxt module and a Nuxt plugin?A module extends the framework during setup and build, while a plugin runs in the app runtime to inject helpers or initialize libraries.
When would you use useState() instead of Pinia?Use useState() for simple shared SSR-safe state and Pinia for larger, more structured application state.
How do you expose env vars to the client?Put them in runtimeConfig.public and use the NUXT_PUBLIC_ prefix so Nuxt can safely expose them.
What is the purpose of server/api/?It holds Nitro API handlers that become backend endpoints like /api/products or /api/login.
What does definePageMeta() do?It lets you attach route-level metadata such as layout, middleware, auth requirements, or page transition settings.
3Advanced Nuxt Interview Questions
QuestionShort answer
What is the difference between SSR, SSG, and CSR in Nuxt?SSR renders on request, SSG prerenders at build time, and CSR renders mostly in the browser after the JS loads.
What is hybrid rendering in Nuxt?It means different routes in the same app can use different rendering or caching strategies based on their needs.
What are routeRules used for?They let you configure behavior per route such as prerendering, redirects, headers, caching, or stale-while-revalidate.
What causes hydration mismatch in Nuxt?It usually happens when server HTML and client HTML differ because of random values, browser-only APIs, timezone differences, or unstable rendering logic.
How do you avoid duplicate API calls in Nuxt?Use stable keys with useAsyncData() or useFetch(), reuse shared fetch state, and avoid triggering the same fetch in multiple uncontrolled places.
How does caching work with Nitro?Nitro supports caching patterns like SWR and route-level caching so repeated requests can reuse generated responses instead of recomputing every time.
How do you keep secrets safe in Nuxt?Keep them in server-only runtime config or environment variables and never expose them through runtimeConfig.public.
How do you deploy Nuxt?You can deploy it as a Node server, serverless output, edge-style target, or static site depending on how the app renders.
How do you debug build or performance issues?Use npx nuxi analyze, inspect payload sizes, lazy-load heavy UI, use route rules correctly, and verify which routes truly need SSR.
What changed in Nuxt 4 that interviewers may ask about?Key points are the default app/ directory, better TypeScript separation, smarter fetch behavior, and faster tooling.
4Scenario-Based Interview Questions
Scenario questionExpected answer direction
How would you build a marketing site with blog pages in Nuxt?I would usually prerender or statically generate public content routes, use useHead() for SEO, and keep only dynamic parts server-rendered if needed.
How would you handle a project with public pages and a protected dashboard?I would use hybrid rendering: prerender or cache public pages, protect dashboard routes with middleware, and verify auth again on the server or backend.
How would you connect Nuxt to an existing Laravel or Node API?I would keep the backend as the source of truth, store base URLs in runtime config, and optionally use Nitro server routes as a proxy or BFF layer.
How would you solve an SEO issue in a Vue SPA by moving to Nuxt?I would move SEO-critical pages into Nuxt routes, render them with SSR or prerendering, and manage metadata with useHead().
How would you optimize a slow product detail page?I would reduce payload size, cache product responses where possible, lazy-load noncritical components, and use route rules for the correct rendering strategy.
How would you migrate a Vue + Vite app to Nuxt?I would create a fresh Nuxt app, move route views into app/pages/, shared UI into app/components/, and convert fetch/state logic incrementally.

Interview tip: do not only define features. Explain why Nuxt helps, which rendering mode you would choose, where the code should live, and what should stay server-only. That makes your answer sound practical instead of memorized.
