A → Z: from basics to advanced, with real examples

Images Containers Dockerfile Compose Dev + Prod

What is Docker?

Docker is a platform for packaging and running applications in containers. A container includes the app code + runtime dependencies + configuration, so it runs the same on any machine.

Think of Docker like a portable runtime box. Instead of “works on my laptop”, you get repeatable environments across dev, testing, and production.

Container = app + dependencies

Your app runs in isolation with consistent libraries and OS-level settings (within the container runtime model).

Image = template

An image is a read-only blueprint used to create containers.

Why we use Docker

1
Consistency

Same app environment everywhere.

# Build once → run anywhere
docker build -t myapp:latest .
docker run --rm -p 8080:8080 myapp:latest
2
Faster setup for dev teams

Spin up full dependencies (DB, cache, app) quickly.

# One command for many services
docker compose up -d
3
Isolation

Apps don’t fight over ports, libraries, or dependency versions.

Useful for running multiple versions and testing.

4
Production-ready workflow

Better deployment repeatability and rollback patterns.

# Push image to registry
docker tag myapp:latest registry.example.com/myapp:1.0.0
docker push registry.example.com/myapp:1.0.0

How Docker works (Flow)

A typical flow
  1. Create an image (Dockerfile → layers)
  2. Run a container from that image
  3. Expose ports to access the app
  4. Persist data using volumes
Minimal example
# 1) Run a public image
docker run --rm -p 8080:80 nginx:latest

Short description: downloads nginx:latest, then runs a container that serves HTML on port 8080.

Dockerfile (How to build your image)

Short description: A Dockerfile is a script that defines how to build an image (base image, install deps, copy code, build app, set command).

Example Dockerfile (simple Node.js app)
# Use an official Node runtime as a parent image
FROM node:20-alpine

# Create app directory
WORKDIR /app

# Copy package files first (better caching)
COPY package*.json ./

# Install dependencies
RUN npm ci

# Copy the rest of the application
COPY . .

# Build (if you have a build step)
# RUN npm run build

# Expose app port (change if needed)
EXPOSE 3000

# Start the app
CMD ["npm", "run", "dev"]

Key idea: Docker builds in layers. Copying package*.json before the rest lets Docker reuse cached layers when only app code changes.

ARG vs ENV
ARG — build-time only

Available only during docker build. Not present in the running container.

ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-alpine

ARG BUILD_ENV=production
RUN echo "Building for: $BUILD_ENV"
# Override at build time
docker build --build-arg NODE_VERSION=18 -t myapp .
ENV — runtime variable

Persists inside the running container as an environment variable.

FROM node:20-alpine
ENV NODE_ENV=production
ENV PORT=3000

# App can read process.env.NODE_ENV at runtime
CMD ["node", "server.js"]

Rule of thumb: Use ARG for build config (versions, feature flags). Use ENV for runtime config (NODE_ENV, PORT, API URLs). Never put secrets in either — they can be read via docker inspect.

ENTRYPOINT vs CMD
CMD — default command (overridable)

Provides defaults. Easily replaced at runtime by passing a command after the image name.

FROM node:20-alpine
WORKDIR /app
COPY . .
CMD ["npm", "start"]
# Overrides CMD entirely at runtime
docker run myapp npm run dev
ENTRYPOINT — fixed executable

Container always runs this executable. Runtime arguments are passed as params to it, not a replacement.

FROM node:20-alpine
WORKDIR /app
COPY . .
ENTRYPOINT ["node", "server.js"]
# CMD provides default args to ENTRYPOINT
CMD ["--port", "3000"]
# Replaces only the CMD args (--port 8080 instead of 3000)
docker run myapp --port 8080
CMDENTRYPOINT
Overridable?Yes — pass a command after image nameOnly with --entrypoint flag
Best forDefault commands, dev containersExecutable / CLI tool containers
Combined useENTRYPOINT = the executable  |  CMD = its default arguments
HEALTHCHECK instruction

Tells Docker how to test if the container is healthy. Used by Compose depends_on: condition: service_healthy and orchestrators.

FROM node:20-alpine
WORKDIR /app
COPY . .
RUN npm ci
EXPOSE 3000
CMD ["node", "server.js"]

# Test every 30s, timeout 5s, 3 retries before marked "unhealthy"
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
  CMD wget -qO- http://localhost:3000/health || exit 1
# See health status
docker ps          # shows (healthy) / (unhealthy) / (starting)
docker inspect --format='{{json .State.Health}}' <container_id>

Docker Compose (Multi-container apps)

Compose is used to define and run multiple containers (app + database + redis) together using a single YAML file.

docker-compose.yml (example: app + Postgres)
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app123
      POSTGRES_DB: appdb
    volumes:
      - db_data:/var/lib/postgresql/data
    ports:
      - "5432:5432"

  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://app:app123@db:5432/appdb
    depends_on:
      - db

volumes:
  db_data:
# Start everything
docker compose up -d

# Stop everything
docker compose down

Networking Basics

Container-to-container

Compose creates a private network. Services can reach each other by service name.

# example from app container
DATABASE_URL=postgres://user:pass@db:5432/appdb
Host-to-container

Use -p hostPort:containerPort to expose your service on the host machine.

docker run --rm -p 8080:80 nginx:latest
Network Types
TypeDescriptionWhen to use
bridgeDefault. Private internal network on the host. Containers on the same custom bridge can reach each other by service name.Most local / dev use cases
hostContainer shares the host network stack directly. No port mapping needed.High-performance networking on Linux
noneDisables all networking for the container.Isolated batch jobs, security-sensitive tasks
overlayMulti-host network spanning multiple Docker daemons (Swarm / distributed services).Docker Swarm, multi-node clusters
 
# Run on host network (Linux only — no port mapping needed)
docker run --rm --network host nginx

# Run with no network access
docker run --rm --network none alpine ping google.com  # fails as expected
docker network commands
CommandPurpose
docker network lsList all networks
docker network create mynetCreate a custom bridge network
docker network inspect mynetDetailed info: connected containers, subnet, gateway
docker network connect mynet <container>Attach a running container to a network
docker network disconnect mynet <container>Detach a container from a network
docker network rm mynetRemove a network (no connected containers allowed)
docker network pruneRemove all unused networks
 
# Create a custom network
docker network create mynet

# Run two containers on it — they can reach each other by name
docker run -d --name db  --network mynet postgres:16-alpine
docker run -d --name app --network mynet -p 3000:3000 myapp:latest

# Inside app container: connect to db on db:5432 (by service name)
Custom named networks in Compose
services:
  db:
    image: postgres:16-alpine
    networks:
      - backend

  app:
    build: .
    ports:
      - "3000:3000"
    networks:
      - backend
      - frontend

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    networks:
      - frontend

# All custom networks must be declared here
networks:
  frontend:
  backend:
    internal: true   # containers only — no outbound internet access

Tip: internal: true isolates the network — containers on it cannot reach the internet. Great for locking down your database network so it is never exposed.

Volumes & Persistence

Containers are ephemeral. Use volumes to keep data across restarts/removals.

Create and inspect volumes
docker volume create mydata
docker volume ls
docker volume inspect mydata
Use a named volume
docker run --rm -it \
  -v mydata:/data \
  alpine:latest sh -c "echo hello > /data/msg.txt; cat /data/msg.txt"
Volume Types: Named vs Bind Mount vs tmpfs
TypeSyntaxManaged byBest for
Named volume-v mydata:/app/dataDockerDB data, persistent app state
Bind mount-v /host/path:/container/pathHost filesystemDev hot-reload, sharing source code
tmpfs--tmpfs /tmpHost RAM (in-memory)Ephemeral scratch space, secrets in RAM
Named volume

Docker manages the storage location. Data survives container deletion.

docker run -d \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16-alpine
Bind mount

Maps a host directory directly. Changes on the host are instantly visible inside the container — ideal for local dev.

docker run -d \
  -v $(pwd):/app \
  -p 3000:3000 \
  myapp:dev
# Compose bind mount
services:
  app:
    volumes:
      - ./src:/app/src
tmpfs mount

In-memory only. Lost on container stop. Fast and secure for temporary data that must not touch disk.

docker run -d \
  --tmpfs /tmp \
  --tmpfs /run:rw,noexec,nosuid,size=64m \
  myapp:latest
docker cp — copy files to/from containers
# Copy FROM container TO host
docker cp <container_id>:/app/logs/error.log ./error.log

# Copy FROM host TO container
docker cp ./config.json <container_id>:/app/config.json

# Copy an entire directory from container
docker cp <container_id>:/app/dist ./dist-from-container

Tip: docker cp works on both running and stopped containers. Useful for pulling build artifacts out of a container without mounting a volume.

Multi-stage builds (Advanced Docker)

Multi-stage builds reduce final image size and improve security by excluding build tools from the runtime image.

Example (build + run)
# 1) Build stage
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 2) Runtime stage
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
# If using Express, adjust CMD accordingly.
EXPOSE 3000
CMD ["node", "dist/server.js"]

Short example outcome: final image contains only runtime artifacts (like dist), not dev dependencies and build tools.

Best practices (Basic → Advanced)

1) Keep images small
  • Use slim/alpine variants when appropriate
  • Use multi-stage builds
  • Clean up caches (package manager)
2) Leverage layer caching
  • Copy lockfiles/package files first
  • Install deps before copying frequently changing code
3) Avoid running as root

Prefer a non-root user in production images.

4) Use .dockerignore

Exclude node_modules, logs, build output, local env files to speed builds.

Security basics

  • Pin image versions instead of using only :latest
  • Minimize attack surface (small images, multi-stage builds)
  • Don’t bake secrets into images or Dockerfile layers
  • Use read-only root filesystem where possible
  • Limit capabilities and run as non-root

Short description: Docker security is mostly about building safer images and controlling runtime privileges.

Performance tips

Build speed
  • Use caching by copying package files first
  • Exclude junk via ignore files
  • Keep Dockerfile instructions ordered from stable → changing
Runtime speed
  • Choose correct base images
  • Reduce layers and image size
  • Use health checks to manage readiness (Compose supports it)

Trending topics (the “most asked” Docker parts)

Docker containers vs VMs (quick difference)
  • VMs: virtualize hardware (run a full guest OS per VM)
  • Containers: share the host kernel; only package app + dependencies
  • Overhead: containers are usually lighter/faster to start
  • Isolation: both isolate workloads, but containers share more OS-level resources

Short description: Containers are like “app sandbox + runtime”; VMs are like “mini computers”.

Build Secrets (Secure secret handling)

Mount secrets during build without baking them into the image. Secrets are only available during the build step and never appear in image layers.

Dockerfile with secrets
# syntax=docker/dockerfile:1
FROM node:20-alpine
WORKDIR /app

# Mount secret during build (only available in this RUN step)
RUN --mount=type=secret,id=npm_token \
    export NPM_TOKEN=$(cat /run/secrets/npm_token) && \
    npm config set //registry.npmjs.org/:_authToken=$NPM_TOKEN && \
    npm install

COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
# Build with secret (secret is NOT stored in image)
echo "npm_secret_token_123" > .npm_token
docker build --secret id=npm_token,src=.npm_token -t myapp .
rm .npm_token

Important: Secrets are only available during the specific RUN step where they're mounted. They're automatically removed after the step completes.

Cache Mounts (Faster builds)

Persist cache between builds to dramatically speed up dependency installation. Cache is stored on the host and reused across builds.

Dockerfile with cache mounts
# syntax=docker/dockerfile:1
FROM node:20-alpine
WORKDIR /app

# Cache npm dependencies between builds
RUN --mount=type=cache,target=/root/.npm \
    --mount=type=cache,target=/app/node_modules \
    npm install

COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
Cache types
  • inline — Cache stored in image layers (default)
  • registry — Cache pushed to registry for CI/CD sharing
  • local — Cache stored in local directory
Cache targets
  • /root/.npm — npm cache
  • /app/node_modules — Dependencies
  • /var/cache/apt — APT cache (Debian/Ubuntu)
Docker Buildx (Multi-platform builds)

Build images for multiple architectures (amd64, arm64, arm/v7) from a single Dockerfile. Essential for supporting Apple Silicon, Raspberry Pi, etc.

# Create a new builder instance
docker buildx create --name mybuilder --use

# Build for multiple platforms
docker buildx build --platform linux/amd64,linux/arm64 \
  -t myapp:latest \
  --push .

# Build and load to local Docker
docker buildx build --platform linux/amd64,linux/arm64 \
  -t myapp:latest \
  --load .

Tip: Use --push to push directly to registry, or --load to load into local Docker. For CI/CD, --push is preferred.

Docker in CI/CD Pipelines

Automate building, testing, and pushing Docker images using CI/CD platforms like GitHub Actions, GitLab CI, or Jenkins.

GitHub Actions Example
.github/workflows/docker.yml
name: Docker Build and Push

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_PASSWORD }}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: |
            myuser/myapp:latest
            myuser/myapp:${{ github.sha }}
          cache-from: type=registry,ref=myuser/myapp:buildcache
          cache-to: type=inline

      - name: Run security scan
        run: docker scan myuser/myapp:latest || true

Best practices: Use ${{ github.sha }} for unique tags per commit. Store registry credentials as GitHub secrets. Use Buildx cache for faster builds.

docker run -d -m 512m nginx:latest

# Limit with swap (total 1GB)
docker run -d -m 512m --memory-swap=1g myapp:latest

# Soft limit (container can exceed if resources available)
docker run -d --memory-reservation=256m -m 512m myapp:latest

Warning: If a container exceeds its memory limit, it will be killed by the OOM (Out Of Memory) killer. Set appropriate limits based on your application's needs.

docker run -d --cpuset-cpus="0,1" myapp:latest

# Give 50% of CPU time (relative weight)

Compose Resource Limits
docker-compose.yml with resource limits
services:
  app:
    build: .
    deploy:
      resources:
        limits:
          cpus: '1.0'
          memory: 512M
        reservations:
          cpus: '0.25'
          memory: 128M
    ports:
      - "3000:3000"

  db:
    image: postgres:16-alpine
    deploy:
      resources:
        limits:
          cpus: '2.0'
          memory: 1G
        reservations:
          cpus: '0.5'
          memory: 256M
    volumes:
      - db_data:/var/lib/postgresql/data

volumes:
  db_data:

Note: deploy resources are only enforced in Docker Swarm mode. For single-host Docker, use cpus and memory directly under the service.

Monitoring Resource Usage
# Live resource usage for all containers
docker stats

# Stats for specific container
docker stats myapp-container

# One-time stats (no streaming)
docker stats --no-stream

# Inspect container resource limits
docker inspect --format='{{.HostConfig.Memory}}' myapp-container
docker inspect --format='{{.HostConfig.CpuShares}}' myapp-container
Best practices
  • Set both limits and reservations
  • Monitor actual usage before setting limits
  • Use --memory-reservation for soft limits
  • Consider OOM score adjustments
Common issues
  • Container killed by OOM → increase memory limit
  • High CPU usage → check for infinite loops
  • Slow performance → check if limits are too restrictive
  • Swap usage → consider disabling swap in container

Security Scanning & Vulnerability Management

Regularly scan your Docker images for vulnerabilities, misconfigurations, and security issues before deploying to production.

Docker Scan (Built-in)

Docker's built-in scanning tool powered by Snyk. Scans for vulnerabilities in OS packages and application dependencies.

# Scan an image for vulnerabilities
docker scan myapp:latest

# Scan with full output
docker scan --file /app/package.json myapp:latest

# Accept or ignore specific vulnerabilities
docker scan --accept HIGH myapp:latest

# Login to Snyk for more features
docker login --username  snyk

Note: Docker Scan requires a free Snyk account for full functionality. Limited scans are available without authentication.

Trivy (Comprehensive Scanner)

A simple and comprehensive vulnerability scanner for containers, filesystems, and repositories. Supports OS packages and language-specific dependencies.

# Run Trivy scanner in a container
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy image myapp:latest

# Scan with specific severity levels
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy image --severity HIGH,CRITICAL myapp:latest

# Generate JSON report
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy image --format json -o report.json myapp:latest

# Scan filesystem (without Docker socket)
trivy fs /path/to/project
Trivy in CI/CD
# GitHub Actions example
- name: Run Trivy vulnerability scanner
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'myapp:latest'
    format: 'sarif'
    output: 'trivy-results.sarif'
    severity: 'CRITICAL,HIGH'

- name: Upload Trivy scan results
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: 'trivy-results.sarif'
Clair (Static Analysis)

An open-source static analysis engine for container vulnerabilities. Often used with Quay.io registry.

# Run Clair scanner
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  quay.io/projectquay/clair-scanner:latest \
  scan myapp:latest

# Using klar (simpler Clair client)
klar myapp:latest
SBOM Generation

Generate a complete inventory of all software components in your container image. Essential for supply chain security.

# Generate SBOM with Syft
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  anchore/syft myapp:latest -o spdx-json > sbom.json

# Generate SBOM with Docker Scout (Docker CLI plugin)
docker scout cves myapp:latest

# Generate SBOM with Trivy
trivy image --format spdx-json -o sbom.json myapp:latest

# View SBOM contents
cat sbom.json | jq '.packages[] | {name, version, licenses}'
SBOM formats
  • SPDX — Linux Foundation standard
  • CycloneDX — OWASP standard
  • SWID — ISO/IEC standard
Why SBOM matters
  • Track all dependencies and licenses
  • Quickly respond to vulnerabilities (like Log4j)
  • Meet compliance requirements
  • Supply chain transparency
Image Signing & Verification

Cryptographically sign your images to ensure they haven't been tampered with and come from a trusted source.

# Sign image with Docker Content Trust
export DOCKER_CONTENT_TRUST=1
docker push myapp:latest

# Verify signature
docker pull myapp:latest

# Sign with Cosign (Sigstore project)
cosign sign myapp:latest

# Verify with Cosign
cosign verify myapp:latest \
  --certificate-identity-regexp=.* \
  --certificate-oidc-issuer-regexp=.*

Best practice: Enable Docker Content Trust in production environments to ensure only signed images can be pulled and run.

Security Scanning Best Practices
CI/CD Integration
  • Scan on every pull request
  • Fail builds on critical vulnerabilities
  • Generate SBOMs for all releases
  • Sign images before pushing to registry
Regular Scanning
  • Schedule daily/weekly scans
  • Monitor for new CVEs in dependencies
  • Update base images regularly
  • Use vulnerability databases
